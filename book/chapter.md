## 핵심 내용

# 웹 크롤러
= 로봇 or 스파이더
: 웹에 새로 올라오거나 갱신된 콘텐츠를 찾아내는 목적을 가진 검색 엔진에서 널리 쓰는 기술
몇 개 웹 페이지에서 시작하여 그 링크를 따라 나가면서 새로운 콘텐츠를 수집
* 콘텐츠 ex) 웹 페이지, 이미지, 비디오, PDF 파일 등

| 명칭 | 설명 |
|---|---|
| 로봇(Robot) | 웹페이지를 자동으로 방문하고 정보를 수집하는 프로그램 |
| 스파이더(Spider) | 웹페이지의 링크를 따라 이동하며 정보를 수집하는 프로그램 |
| 웹 크롤러(Crawler) | 로봇, 스파이더와 같은 의미로 사용되는 용어 |

# 크롤러의 이용
- 검색 엔진 인덱싱 : 웹 페이지를 모아 검색 엔진을 위한 로컬 인덱스를 만듬 ex) Googlebot
- 웹 아카이빙 : 나중에 사용할 목적으로 장기 보관하기 위해 웹에서 모음 ex) 미국 국회 도서관, EU 웹 아카이브
- 웹 마이닝 : 인터넷에서 유용한 지식을 도출해 내는 것 ex) 주주 총회 자료, 연차 보고서 등에 사용
- 웹 모니터링 : 저작권, 상표권 참해 사례 모니터링 ex) 디지마크사

# 웹 크롤러의 기본 알고리즘
1. 입력 [ URL 집합 ] → 해당 모든 URL의 모든 웹페이지를 다운로드
2. 다운받은 웹 페이지에서 URL 추출
3. 추출된 URL들을 다운로드할 URL 목록에 추가하고 위의 과정을 처음부터 반복함

But, 규모 확장성을 갖는 웹 크롤러 설계는 어렵고 이렇게 단순하게 동작하지 않음

# 웹 크롤러 만족 속성
- 규모 확장성 : 규모가 크므로 병행성을 활용해 효과적으로 진행하기
- 안정성 : 웹에는 함정이 많아 비 정상적 입력이나 환경에 잘 대응해야 함
- 예절 : 짧은 시간 너무 많은 요청을 보내서는 안된다
- 확장성 : 새로운 형태의 콘텐츠를 지원하기 쉬워야 함. 전체 시스템 새로 설계 X

# 요구사항에 맞게 설계 예시
- 일일 웹 다운로드 수 : 10억
- QPS = 10억 / 30일 / 24시간 / 3600초 = 약 400 페이지/초 
- 최대 QPS = 2 x QPS = 800
- 웹 페이지 크기 평균 = 500k
- 10억 페이지 x 500k = 500TB/월 (2의 제곱수)
- 데이터 5년 보관 = 500TB x 12 x 5 = 30PB

# URL 단축
: URL 짧게 줄임. 긴 URL을 해시 값으로 대응시킬 함수 fx를 찾는 것 (= 긴 URL을 짧은 문자열로 변환하고, 나중에 그 문자열로 원래 URL을 찾을 수 있도록 만드는 것)

ex) 입력 URL 다른 값이면 해시 값도 달라지고, 계산된 해시 값은 원래 입력 URL로 복원되어야 함

# URL 리디렉션 (리다이렉션)
: 단축 URL로 HTTP 요청이 오면 원래 URL로 안내

- 301 응답 : Permanently Moved
HTTP 요청 처리 책임이 영구적으로 Location 헤더에 반환된 URL로 이전
같은 단축 URL 요청시 캐시 사용함
장점 : 첫번째 요청만 단축 URL로 전송되어 서버 부하 줄일수 있음
단점 : 영구적인 이동을 의미하므로 URL 변경이 잦은 서비스에는 적합하지 않음

- 302 응답 : Found
주어진 URL로의 요청이 일시적으로 Location 헤더가 지정하는 URL에 의해 처리되어야 함
무조건 단축 URL 서버에 보내진 후, 원래 URL로 리디렉션 되어야 함
장점 : 클릭 발생률이나 발생 위치 추적 등 트래픽 분석이 가능
단덤 : 요청할 때마다 단축 URL 서버를 거치므로 서버 부하가 증가하고, 서버 요청이 많아져 응답 시간이 늘어날 수 있으며 트래픽이 많아질수록 서버 운영 비용이 증가할 수 있음

# API 엔드포인트
: 클라이언트가 서버의 특정 기능을 사용하기 위해 요청하는 URL 주소, API 엔드포인트를 통해 서버와 통신함 // ex) RESTful API 방식
- URL 단축용 엔드포인트 : 단축할 URL 파라미터 보냄 (POST 요청) // ex) POST/api/v1/data/shorten
* 인자 : longUrl : longUrlstring / 반환 : 단축 URL
- URL 리디렉션용 엔드포인트 : 원래 URL로 보내주기 위한 용도 (HTTP 요청) // ex) GET/api/v1/shortUrl

# URL 단축 플로
단축 URL 입력 (브라우저) → 원래 URL 변환 (URL 받은 서버) → 301 응답 반환 → 원래 URL 방문

# 데이터 모델
1) 해시 테이블
초기에는 괜찮으나 실제 시스템에는 메모리가 유한하고 비싸기 때문에 쓰기 어렵다.
2) 순서쌍 DB 저장
<단축 URL, 원래 URL> 순서쌍을 관계형 데이터베이스에 저장
3) 해시 함수 (단축 URL을 hashValue 라고 가정)
: 원래 URL을 단축 URL로 변환. 
- 해시 값 길이 : 62<sup>8</sup> // 0-9, 대/소문자 A-Z 총 62개 문자로 구성
- 해시 함수 구현 (해시 후 충돌 해소, base-62 변환)

# 해시 후 충돌 해소
해시함수를 통해 긴 URL을 7글자 문자열로 줄임
해시함수 ex) CRC32, MD5, SHA-1
But, CRC32 로 계산한 짧은 해시값도 7보다는 긴 문제 발생
이를 해결하려 처음 7 글자만 이용하게 되면 충돌 확률이 높아져 실제 충돌이 일어났을 때는 충돌 해소 될때까지 사전에 정한 문자열을 해시값에 덧붙인다.

# base-62 변환
수의 표현 방식이 다른 두 시스템이 같은 수를 공유할때 유용함
흔히 사용되는 접근법으로 10진수 → 62진수 진법 변환이다.
ex) 11157<sub>10</sub> → 2TX<sub>62</sub>

# 두 접근법 비교
| 구분 | 해시 후 충돌 해소 전략 | Base62 변환 |
|---|---|---|
| 단축 URL 길이 | 고정 길이 | 가변 길이 (ID 증가에 따라 길어짐) |
| 고유 ID 생성 | 불필요 | 필요 |
| 충돌 가능성 | 충돌 가능, 해소 전략 필요 | 고유 ID 보장 시 충돌 없음 |
| URL 예측 가능성 | 다음 URL 예측 불가 (ID 기반 계산 방식 아님) | 순차 증가 ID 사용 시 다음 URL 예측 가능 (보안 문제) |

# 상세 설계 예시
1. 긴 URL을 받고 DB 에서 해당 URL이 있는지 검사. 있다면 해당 단축 URL을 반환
2. 없다면 62진법 변환을 통해 단축 URL을 만들고 (DB 저장), 해당 URL을 반환
3. URL 리디렉션 캐시에 <단축URL, 원래URL> 저장하면 읽기 성능이 높아짐

* 로드 밸런서 동작 흐름
단축 URL 클릭 → 로드밸런서가 웹 서버에 요청 전달 → 캐시가 있는 경우 단축 URL에 매칭되는 원래 URL을 전달 → 없는 경우 DB에서 전달하고 캐시에 저장한다 → 사용자에 반환

## 면접 예상 질문
1. **Q. URL 단축기는 어떤 방식으로 동작하나요?**  
   **A.** 긴 URL을 짧은 문자열로 변환하여 DB에 저장하고, 사용자가 단축 URL에 접속하면 원래 URL을 조회한 뒤 301 또는 302 응답을 통해 리디렉션합니다.

2. **Q. URL 단축 시 해시 후 충돌 해소 방식과 Base62 변환 방식의 차이는 무엇인가요?**  
   **A.** 해시 방식은 충돌 가능성이 있어 별도의 충돌 해소 과정이 필요합니다. 반면 Base62 방식은 고유 ID를 62진수로 변환하므로 ID의 유일성이 보장되면 충돌이 발생하지 않습니다.

3. **Q. URL 리디렉션에서 301과 302 응답의 차이는 무엇인가요?**  
   **A.** 301은 영구적인 이동으로 브라우저 캐싱을 통해 서버 부하를 줄일 수 있습니다. 302는 일시적인 이동으로 클릭 수 추적과 트래픽 분석에 유리하지만 서버 요청이 증가할 수 있습니다.

4. **Q. URL 단축기에서 높은 가용성과 규모 확장성을 어떻게 확보할 수 있나요?**  
   **A.** 로드 밸런서를 통해 요청을 여러 웹 서버에 분산하고, 캐시를 활용해 DB 조회 부하를 줄입니다. 또한 웹 서버 증설과 DB 다중화 및 샤딩을 통해 규모 확장성과 가용성을 높일 수 있습니다.
