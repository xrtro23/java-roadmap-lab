# tiny url
TinyURL : 긴 URL 주소를 짧은 URL로 변환해 주는 서비스

Q) 기존 POST 방식으로 보고 있는 화면을 외부 링크로 접속할수 있게 첨부하려고 하면
ex) https://example.com/expBuyPrint?pageNm=buyPrint&BOrderCd=F-B-20261105-0001&email=test@example.com 
이런 것처럼 GET 방식을 쓴다고 했을때 주소가 길어질거 아니야? 이런 경우에도 단축키 적용을 해서 짧게 하는것도 가능한가?

A) 적용 가능. 예시) https://tinyurl.com/abc123
But. 단순 공유용이면 DB에 저장하고 자체 토큰으로 URL 불러오는 방식이 더 나을수 있음.

#  높은 가용성과 규모 확장성, 장애 감내가 요구됨의 예시
Q) 단축 URL 에서의 높은 가용성과 규모 확장성, 장애 감내가 요구됨의 예시를 알려줘
A) 높은 가용성 : 서비스가 언제든지 정상적으로 작동 ex) 사용자가 단축 URL에 접속하면 언제든 원본 URL로 이동
규모 확장성 : 사용자가 많아지더라도 서비스를 안정적으로 처리 // 개략적 추정과 유사한 내용
장애 감내 : 일부 시스템에 장애가 발생해도 전체 서비스가 중단되면 안됨 ex) 서버 A가 고장 나면 서버 B가 대신 단축 URL 리다이렉션을 처리

# API 엔드포인트 
클라이언트가 서버의 특정 기능을 사용하기 위해 요청하는 URL 주소.
URL 단축용 (POST) : 긴 URL을 서버에 전달하면 단축 URL을 생성하여 반환.
URL 리디렉션용 (GET) : 단축 URL로 접속하면 서버에서 원본 URL을 조회하여 해당 주소로 이동시킴.

Q) RESTful API 방식 과 아닌 것 예시를 들어서 설명해줘. md 파일 표 형태로 정리 부탁해
A) RESTful API 방식
클라이언트가 서버의 특정 기능을 사용하기 위해 요청하는 URL 주소.
RESTful API는 자원(Resource)을 중심으로 URL을 설계하고, HTTP 메서드를 통해 동작을 구분한다.

| 구분 | RESTful API | 비RESTful API 예시 |
|---|---|---|
| URL 특징 | 자원(명사) 중심 | 동작(동사) 중심 |
| 조회 | `GET /api/users/10` | `GET /api/getUser?id=10` |
| 생성 | `POST /api/users` | `POST /api/createUser` |
| 수정 | `PUT /api/users/10` | `POST /api/updateUser` |
| 삭제 | `DELETE /api/users/10` | `POST /api/deleteUser` |

| 기능 | RESTful 방식 | 동작 중심 방식 |
|---|---|---|
| 단축 URL 생성 | `POST /api/v1/urls` | `POST /api/v1/data/shorten` |
| 단축 URL 조회 | `GET /api/v1/urls/abc123` | `GET /api/v1/getShortUrl?code=abc123` |
| 단축 URL 삭제 | `DELETE /api/v1/urls/abc123` | `POST /api/v1/deleteShortUrl` |
| 리디렉션 | `GET /abc123` | `GET /api/v1/redirect?code=abc123` |

* 정리
- RESTful API : URL은 자원(명사), HTTP 메서드는 행위(GET, POST, PUT, DELETE)를 표현한다.
- 비RESTful API : REST 설계 원칙을 따르지 않는 API를 의미한다.
- RESTful API는 URL만으로 결정되지 않으며 무상태성, 일관된 인터페이스 등의 원칙도 고려해야 한다.
- URL에 동사가 포함되었다고 무조건 비RESTful인 것은 아니다.
- 단축 URL의 리디렉션은 GET 요청을 통해 원본 URL로 이동시키는 기능이다.

# 301, 302
Q) 301, 302 장단점 간단하게만 표로 정리해
A)
| 구분 | 301 (Moved Permanently) | 302 (Found) |
|---|---|---|
| 의미 | 영구적인 URL 이동 | 일시적인 URL 이동 |
| 캐싱 | 브라우저 캐싱 가능 | 기본적으로 캐싱되지 않음 (별도 설정 가능) |
| 장점 | 서버 부하 감소, 응답 속도 향상 | 클릭 수 및 트래픽 분석 용이, URL 변경에 유리 |
| 단점 | 클릭 추적 어려움, 캐시된 URL 변경 어려움 | 서버 부하 증가, 응답 시간 및 운영 비용 증가 |
| 사용 목적 | URL 변경 가능성이 낮은 경우 | 클릭 분석이나 URL 변경이 필요한 경우 |

# 해시 함수 (CRC32, MD5, SHA-1)
Q) 각 해시 함수 정리 좀 해줘
A) 
| 구분 | CRC32 | MD5 | SHA-1 |
|---|---|---|---|
| 해시 길이 | 32비트 | 128비트 | 160비트 |
| 주요 용도 | 데이터 오류 검출 | 데이터 무결성 확인 | 데이터 무결성 확인 |
| 장점 | 계산 속도가 빠름 | 빠르고 구현이 간단함 | MD5보다 해시 값이 길어 충돌 가능성이 낮음 |
| 단점 | 충돌 가능성이 높음 | 충돌 취약점 존재 | 충돌 취약점 존재 |

- 해시 충돌 : 서로 다른 입력 데이터가 동일한 해시 값을 가지는 현상
- CRC32는 암호학적 해시 함수가 아닌 오류 검출용 함수
- MD5와 SHA-1은 보안 목적으로 사용하기에 안전하지 않음
- URL 단축에서는 해시 값의 일부를 사용할 수 있지만, 충돌 처리 로직이 필요함

# Base62 변환
Q) Base62 변환이 이해가 안가
A) 62진법을 사용함 (우리가 평소 사용하는 숫자는 10진법)
같은 숫자를 더 적은 자릿수로 표현할 수 있다.
DB에서는 ID를 10진수 숫자로 관리하고, URL에서는 62진수 문자열로 표현함.
두 시스템은 표현 방식만 다를 뿐 같은 숫자(ID)를 사용함.

Q) ex) 11157<sub>10</sub> → 2TX<sub>62</sub>
이게 어떻게 2TX가 나와? 11157을 62로 나눈 건 아는데 그 뒤를 이해 못함.

A) 62로 계속 나누면서 나온 나머지를 Base62 문자로 변환한 후 역순으로 읽는 방식

0 to 9 → 숫자 0~9
10 to 35 → 소문자 a~z
36 to 61 → 대문자 A~Z

상세 내용은 검증 쪽에 정리함.

## 어떻게 검증했나

1. 10진수 11157를 base-62 변환 검증 대조 실험

| 계산 | 몫 | 나머지 | Base62 문자 |
|---|---|---|---|
| 11157 ÷ 62 | 179 | 59 | X |
| 179 ÷ 62 | 2 | 55 | T |
| 2 ÷ 62 | 0 | 2 | 2 |

- 나머지를 순서대로 변환하면 X → T → 2
- 나머지는 낮은 자릿수부터 구해지므로 역순으로 읽어야 함
- 따라서 11157<sub>10</sub> = 2TX<sub>62</sub>

검증 : 2 × 62<sup>2</sup> + 55 × 62<sup>1</sup> + 59 × 62<sup>0</sup> = 11157
